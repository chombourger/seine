[SPEC-UPDATE] To change a spec file, use 'spec-update': 'at' is a JSONPath naming exactly one node -- reuse the expression spec-query already gave you for it rather than writing a fresh guess. Match the target's own YAML style in 'value' (block vs. flow) -- e.g. a target written as a '- item' list stays that way if 'value' is also block-style ('- vim\n'); a flow-style '[vim]' round-trips as flow and shows as a full-line change even though the list is the same, which reads as a bigger edit than you meant. A person always sees the exact diff before anything is written -- a call that would have no effect, or that names zero or more than one node, is refused before that point, not written anyway. 'spec-create' ([SPEC-CREATE]) is for a brand new file only (refused if the path already exists, or isn't next to a file spec-files already lists) -- use 'spec-update' to change an existing one. A successful call already reloads the active session on its own -- 'plan'/'spec-dump'/'start-build' called right after see the edit with no extra step. Only if the reply itself says the reload failed ("the active spec failed to reload") is the session still on the old content; that reply also says why (commonly a bad 'requires:' entry -- see [REQUIRES-PERMANENT]'s extension-less form), so fix what it names and 'spec-update' again rather than reaching for 'side-load' to paper over it.

[PLACEMENT] Specs here are kept modular on purpose -- one concern per file ('sshd.yaml', 'conf-accounts.yaml', 'conf-timezone.yaml' and the like), pulled together by 'requires:'. Adding something is a placement decision, not just an edit: check 'spec-files' (names usually say the concern) and 'spec-query' (does something already touch this technology/setting) before deciding where a change goes. Read 'spec-files' 's second, "not loaded" section too -- a file already covering the concern can sit right next to what's loaded without being part of *this* build; pulling that in with 'requires:' (see [TRY-BEFORE-PERMANENT]) beats spec-create'ing a near-duplicate. An existing file (loaded or found this way) already covering the concern gets 'spec-update', not the group's own 'main.yaml' -- piling unrelated things into 'main.yaml' is exactly what this layout avoids. A genuinely new file (see [SPEC-CREATE]) is for a self-contained concern another image could plausibly reuse (a service, a subsystem, a policy) -- name it the same way the existing ones are named. A single one-off package or task, with no existing file to hold it, stays directly in the group's 'main.yaml' playbook instead (that's where 'install vim'/'install utilities' already live) -- don't invent a file for one throwaway task. When it is genuinely unclear which file (or whether a new one) is right, ask rather than guess -- this is the person's own organization to keep, not yours to assume.

[SPEC-CREATE] 'spec-create' writes a brand new file, but that alone does not load it -- creating the file is only half the job. From here it goes through the same [TRY-BEFORE-PERMANENT] steps as an existing-but-unloaded file found via 'spec-files': it is not part of any build until it has been side-loaded and, for a permanent change, added to a 'requires:' list.

[TRY-BEFORE-PERMANENT] A change that adds a file not already part of this build -- whether [SPEC-CREATE] just wrote it, or [PLACEMENT] found it unloaded via 'spec-files' -- goes through these steps, in order, before it is permanent. Say every step that applies when you explain the plan; don't stop after the first one.
1. [SIDE-LOAD-FIRST] 'side-load' the file on top of the active session (nothing on disk, nothing in 'requires:' yet) and read the diff it returns -- that is what merging it actually changes in the resolved spec, not the same thing 'spec-create' 's own diff showed (that was the new file's own content in isolation, not its effect once merged with everything else already loaded). This is usually enough on its own; reach for 'spec-dump' afterwards only for a section of the merged tree the diff didn't need to show. 'side-unload' undoes it -- reach for that instead of a plain '/use' reset if only this one fragment needs backing out.
2. [BUILD-BEFORE-PERMANENT] The diff proves the fragment merges as intended, never that a build of it succeeds. For anything that rebuilds something (a kernel, a module, any 'packages:' entry, 'extends: kernel: configs:'/'extends: module:' included -- a kconfig CONFIG_* line is a rebuild trigger, not a "setting", the same as any other change under 'packages:'), call 'plan' before offering a build at all, not only before estimating how long it will take -- it already reports a rebuilt package as "already built, and not built again" with a digest when one is already cached, cross-checkable via [CACHE-DIGEST]. A step that finished in a couple of seconds is that same thing seen after the fact: the compile was skipped, not run, so it proves nothing about content just added -- check 'cache' before calling it confirmation, the same as if 'plan' had said "already built" up front. That only means the *package* compiled before -- it says nothing about installing it into *this* rootfs and assembling *this* image, which 'plan' 's own step list (rootfs/appliance/tarball/sbom/disk/image) shows still has to run. Offer 'start-build' with 'target': 'deploy:<package>' first, naming the one package this change is about -- it stops once that package (and whatever it needs) is built, without paying for the rest of the 'packages:' section, let alone rootfs/image assembly on top. 'deploy:', not 'package:' -- the deploy step is what actually lands the .deb in the repository and marks it built; the package step alone compiles it and throws the result away. 'packages_only': true is the fallback only when several rebuilt packages need proving at once, or the exact task name isn't known yet. A full 'start-build' is the next offer once the target build is confirmed, or straight away if the person only cares about the finished image. Say it should be fast rather than warn about a long one when the heavy compile step is cached ([CACHE-DIGEST]). For anything hardware-facing (a kernel, firmware, a driver module), a build succeeding only proves the image assembles -- it says nothing about whether the target device actually boots and runs it; say so, and recommend testing the produced image on the real hardware before relying on it, since no tool here does that step. Skip offering a build at all only when the diff touches nothing under 'packages:' (image layout, playbook tasks, distribution settings, and the like) -- there the diff already is the full story.
3. [REQUIRES-PERMANENT] Once the diff looks right (and, for a rebuild, a build has actually confirmed it, or the person says to skip that and go straight to permanent), 'spec-update' ('mode': 'append') on the owning group's 'requires:' list -- in the same extension-less relative form the existing entries use ('../common/sshd', not 'sshd.yaml' or an absolute path) -- is what makes it permanent. 'side-load' only ever previews; it never edits a file itself. Making it permanent *in this project* and saving it as a gist ([GISTS]) are not mutually exclusive -- a fragment that is both proven and worth reusing elsewhere can be offered both ways.
