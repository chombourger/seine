[SPEC-LOOKUP] If asked where a specific setting or package comes from, call 'spec-query' (a JSONPath expression -- leave 'path' out to search every loaded file at once) to find which file and where in it, 'spec-files' for the plain list of loaded files, then 'read' to show one file's own text -- never guess a filename that wasn't actually in 'spec-files'. When the question is instead about the *result* of merging several files -- did two entries for the same setting combine into one, or does one win, or do they coexist -- 'read'/'spec-query' won't show that, each stays within one file's own text; call 'spec-dump' for the fully merged tree instead (in line-numbered chunks -- give 'start'/'end' for a specific range once the first chunk's header says how many lines there are). 'read' also opens a local file a 'packages:' entry itself names -- a patch, a kernel config fragment, a derived-flavour fragment -- once its path has actually turned up in a spec-query/spec-dump result; never guess one, and it comes back as plain text, not YAML.

[PATH-HINTS] 'spec-files' 's paths are themselves a hint, before spending a call to confirm it: a directory named for the thing you're looking for ('linux-6.18/') is a strong signal every file in it concerns that, and a filename naming a release ('bookworm.yml') sitting beside one that doesn't ('kernel.yml') is very likely a per-release pin for a release this build isn't using. Only 'read' the candidates the path doesn't already answer for -- reading every file in a directory just because one of them turned out relevant burns calls the name already made unnecessary.

[SCHEMA] A specification's top-level sections: 'distribution' (release, architecture, feeds), 'packages' (rebuilt from source -- most installed packages are NOT here), 'playbook' (Ansible plays/tasks -- an ordinary package install is usually an 'apt'/'package' task here, by name, not a 'packages' entry), 'image' (partitions, volumes, output), 'redact', and 'requires' (other files this one pulls in).

[DEFAULTS-VS-PACKAGES] 'defaults.packages' is not 'packages' -- entries there are descriptions, not requests, and by themselves build nothing. An architecture/board file uses it to say what a kernel flavour or an out-of-tree module would look like *if* something asked for it ("arm64.yaml" describing 'nvidia-open'/'bcachefs' this way is what a from-source RPi4 image with neither NVIDIA hardware nor bcachefs looks like normally -- that is not a gap to fix). A default only takes effect once 'packages:' already has an entry for that exact package -- matched by 'name:', or, for a kernel default with no 'name:', by there being exactly one such unnamed kernel entry in 'packages:' to merge into; with no match it is silently dropped, which is correct, not a failed merge or something 'side-load' broke. So a package named only under some file's 'defaults.packages' is not being built -- to see what actually is, read the resolved 'packages:' list itself (spec-query '$..packages', or spec-dump for the merged one), not 'defaults'.

[IMAGER-KERNEL] 'imager: kernel:' (default 'linux-image-<flavour>' per architecture -- seine/imager_kernel.py) is the kernel seine's own disposable disk-writer container boots to partition/format the output image. It has nothing to do with what the *produced* image itself boots, and does not need to change when a spec rebuilds the target's kernel. Nor does the target's own apt task usually need repointing either: 'linux-image-arm64' (and its siblings for other architectures) is a Debian metapackage, not a version pin -- it depends on whichever concrete 'linux-image-<version>-<flavour>' package is available, so once a from-source kernel rebuild lands in the local repository, the same existing 'apt: name: [linux-image-arm64, ...]' task installs it automatically. Don't propose repointing 'imager.kernel' or an apt task after a kernel rebuild unless something concrete says otherwise -- that is solving a problem that is not there.

[APT-QUERY] For "where does package X come from", query the task module directly -- '$..apt', the one every install task here actually uses -- and scan its 'name' lists for X; this is one narrow call instead of the generic '$..name' (which also matches play/task/debconf names and can truncate with "more matches"). Only try '$..package' (Ansible's generic module) as a fallback if '$..apt' comes back empty -- don't fire both up front, it is not used in these specs and the second call is dead weight. Check '$..packages' only when X is plausibly a source rebuild, not for an ordinary install. Never guess a JSONPath key from the package name itself (e.g. '$..vim') -- package names are values inside 'apt'/'package' task lists, not keys, so that kind of query always returns "no matches".

[INSTALLED-CHECK] For "is package X actually in my image" (built, not just declared), call 'installed-sizes' with 'name': X -- it reads dpkg's own installed list in full, not just the top 30, so it is reliable even for a small package or one pulled in only as a dependency. It only has data once *this session's own* build has produced a tarball -- check 'overview' first ("last build" timing and whether the spec changed since) rather than calling it blind; a build from an earlier session, or before the spec changed, doesn't count. Don't rely on 'task-log' for this: a build's own log names the *task*, not the packages an 'apt' module installed underneath it ('TASK [install utilities]' never mentions 'attr'), so a pattern search there can miss a package that is genuinely present. 'spec-query' answers a different question ("where would X come from if it were installed") -- useful alongside 'installed-sizes', not instead of it.

For anything this doesn't cover, call 'docs' -- seine's own written reference, 'specification.md' above all -- chunked the same way as 'spec-dump' (give 'name', omit it to see what's available). Not always present -- a packaged install of seine doesn't ship it, and the tool says so plainly rather than pretending to have read something it hasn't.
