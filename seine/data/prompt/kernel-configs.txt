[KERNEL-CONFIGS] For "build the kernel with these CONFIG_X=... options", find which package entry already builds this image's kernel, in order. First, a 'packages:' entry with 'extends: kernel:' among spec-files' *loaded* files ([SPEC-LOOKUP]) -- an entry living only under some file's 'defaults.packages' doesn't count ([DEFAULTS-VS-PACKAGES]) -- that describes a kernel rather than building one. Loaded, that file is where the group goes -- spec-update it directly, never spec-create a second kernel entry beside it. Not loaded, don't reach for a "not loaded" file just because 'kernel' is in its name or path: one naming 'upstream:' pins a kernel tree/version of its own, and requiring it swaps the image's kernel for that tree as a side effect of what was only meant to be a config change -- a far bigger change than asked, and one that also drops whatever Debian security updates were keeping the stock kernel current. A not-loaded file is only safe to require if it builds the *same* kernel this image would otherwise get (an ordinary Debian-flavour rebuild, no 'upstream:' of its own) -- read it first to check, never assume from the name. When nothing loaded or safely reusable exists, 'spec-create' ([SPEC-CREATE]) a new, minimal file: 'packages:' with one entry, 'source: apt://linux' and 'extends: kernel: configs:' -- nothing else. Don't copy 'upstream:'/'drop-patches'/'profiles'/anything else off whatever kernel file was read along the way, even as a starting template -- that drags along settings (an upstream tree pin, above all) the person never asked for. The minimal entry alone already rebuilds the same kernel version currently in use, which is the point. Go through [TRY-BEFORE-PERMANENT] the ordinary way from there. Either way, 'extends: kernel: configs:' is a dictionary of group-name to a list of 'CONFIG_OPTION=value' (or kconfig's own '# CONFIG_OPTION is not set') lines, sitting beside that entry's other 'extends: kernel:' settings. On an existing entry, read the node with 'spec-query'/'read' first: 'spec-update' has no way to add a new dictionary key on its own, so 'value' has to be the *whole* 'configs' mapping (every existing group plus the new one), or the whole 'extends: kernel:' block with 'configs' added if there is none yet -- written with 'mode': 'set' at whichever of those two already exists as a node. Pick a short kebab-case name for what the options are for and say it in the plan -- a person can rename it before approving ([GATED]). Once written, follow [BUILD-BEFORE-PERMANENT]: offer 'start-build' with 'target': 'deploy:linux' (or whatever the package's own name is) first, to prove the kernel actually compiles with it, and the same hardware caveat -- a successful build says nothing about whether the option actually works on real hardware -- say so every time, not only when asked.
