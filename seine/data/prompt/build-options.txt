[BUILD-OPTIONS] 'options' and 'profiles' are sibling attributes on a 'packages:' entry, alongside 'source'/'patches'/'extends:'. 'options' becomes 'DEB_BUILD_OPTIONS' (the package's own debian/rules reads it straight from the environment); 'profiles' becomes sbuild's '--profiles' (dpkg's own build-profile mechanism, which can also gate what the package build-depends on, not only what its rules do). Both are lists of bare tokens ('nocheck', not 'nocheck: true' or '--nocheck') -- read the node first with 'spec-query'/'read' the same as [KERNEL-CONFIGS] describes, then 'spec-update' with 'mode': 'append' onto whichever list already exists, or 'mode': 'set' with the whole entry if the field is new. This is a 'packages:' change like any other, so [TRY-BEFORE-PERMANENT] applies the same way a CONFIG_ line does -- side-load, prove it with a targeted 'start-build', then make it permanent.

Skipping a package's own test suite is 'profiles: [nocheck]', not 'options: [nocheck]', even though Debian policy nominally lists 'nocheck' as a DEB_BUILD_OPTIONS token: dpkg-buildpackage itself propagates a 'nocheck' *profile* into DEB_BUILD_OPTIONS, and, unlike setting the option alone, also drops whatever test-only build-depends the package declares under '<!nocheck>' -- shorter to write and more complete besides. This codebase's own example ('specification.md's busybox one) and its tests only ever write it as a profile -- follow that, don't add a matching 'options: [nocheck]' beside it, it would be redundant. 'options' is for what has no profile equivalent: 'parallel=1' is the one already documented here, for a package whose build breaks under concurrency (see 'building.md' on '--jobs'/'--parallel', which divide the machine across builds *running*, not within one -- 'parallel=1' pins this one package regardless of that division). Debian policy lists a few other DEB_BUILD_OPTIONS tokens ('nostrip', 'noopt', 'terse') that work the same way but have no existing example in this codebase to point at.

For a kernel entry specifically, the easy speed-ups are profiles, documented in 'kernels.md' rather than repeated stale here -- fetch it ('docs' with 'name': 'kernels.md') before naming one, since which profiles the kernel packaging defines, and what each drops, is packaging detail that can change between checkouts. As of the last time this was written: 'noudeb' is effectively required once a fragment removes drivers (the debian-installer udeb check otherwise fails at the very end of a long build, not the start); 'pkg.linux.nokerneldbginfo'/'notools'/'nosource', plus the standard 'nodoc', are pure savings -- packages sized like or larger than the kernel itself that an image never installs anyway. A profile the kernel packaging does not define is accepted and silently ignored, not reported -- say so if asked why naming one had no visible effect, rather than assuming it must have taken hold.
