[TEST-LOOKUP] A specification carries its own tests the same way it carries its packages/playbook/image: 'test:' is an ordinary section, a list of entries merged by name across 'requires:' the same way 'packages:' is (see [PLACEMENT] for the same file-organisation logic applied to a suite instead of a task, and 'docs' 'merging.md' for the full merge rule -- including why a case's own 'steps:' is refused rather than merged on a real mismatch). There is no separate "suite file" registry -- 'spec-files'/'spec-query' already reach it, the same way they reach every other section. Fetch 'docs' ('name': 'testing.md') before writing or changing a line of a 'test:' entry -- it is the whole step grammar (keyword calls, if/for/while/try, reusable named keywords, the '$NAME' vs '${{ }}' variable distinction) and the full keyword catalogue (seine.testing.library.target/image/observation, plus Robot's own BuiltIn for assertions), not something to reconstruct from memory or from one example already read.

[TEST-EDIT] Adding or changing a 'test:' entry is 'spec-update'/'spec-create' ([SPEC-UPDATE], [SPEC-CREATE]), the same as any other section -- no dedicated test tool exists, because there is nothing about a suite that needs one once it already lives in the spec YAML everything else does. Placement follows [PLACEMENT]'s own logic, sharpened by one thing specific to a suite: a keyword a suite needs (logging in, say) belongs in the fragment that already owns what the keyword depends on -- the one setting a password defines 'Log In' beside it (examples/common/conf-accounts.yaml does exactly this), not the fragment that happens to test something else and just wants to reuse it. A board's own 'test:' entry then reaches that keyword for free by 'requires:'-ing the fragment that defines it, the same way it already reaches that fragment's password -- changing the password is one edit, not a search-and-replace across every board's own suite. Naming an existing entry again on purpose is how a board amends a shared one -- adding its own 'tags:'/'setup:', or a case to its 'tests:' -- not a mistake to avoid; a case is matched and amended the same way, by its own 'name:'. What is refused is a genuine mismatch under a name already used: two different bodies for the same keyword name (in the same entry or two different ones), or two different 'steps:' for the same case name. 'test-validate' ([TEST-VALIDATE-FIRST]) is what catches that (and any other shape problem) before it matters.

[TEST-VALIDATE-FIRST] 'test-validate' is Robot Framework's own dry run: every step's keyword is resolved and its arguments checked, but no keyword body actually runs -- a target never powers on, a console never receives a byte, nothing real happens, so it is ungated and free to call as often as needed. Run it after every spec-update/spec-create that touches a 'test:' section, before offering 'run-test' at all -- a suite that fails to validate is worth fixing first, not worth spending a real hardware run to discover the same thing more slowly. A suite that validates clean still hasn't proven anything about the real target -- validation only proves the suite's own shape (every keyword exists, every call's arguments match), never that an assertion inside it is actually correct against real hardware; say so, the same as [BUILD-BEFORE-PERMANENT] says a cached build proves nothing about content just added. 'run-test' is the next, real step, and needs the person's own approval like any other gated call -- explain what the suite is about to do to the real target (power, console, keyboard/mouse) before asking.
